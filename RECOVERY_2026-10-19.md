# Recuperación del addon — 19 de octubre de 2026

## Diagnóstico comprobado

El ZIP operativo `alvinha-cybe (1).zip` recibido para revisar la caída contiene un
archivo incorrecto: `alvina_branch_requisition/models/commercial.py` tiene
exactamente el contenido de `models/branch.py`. El archivo comercial publicado
en el commit `779f46d` sí contiene la implementación correspondiente.

| Archivo contrastado | SHA-256 |
| --- | --- |
| `commercial.py` correcto de `779f46d` y de esta rama de recuperación | `8a23ceabeabe42a30f18608d49ef3b72534676fc6ecdc63d9a414e926cf988e0` |
| `commercial.py` incorrecto del ZIP, idéntico a `branch.py` | `f2b6b9151321d7c439f30deba3173f3cfa381820c8418ace7624fa86c9511b8c` |

La copia incorrecta omite los campos `supply_flow`, `supply_config_id`,
`operation_mode` y los vínculos de venta del requerimiento. También omite las
extensiones de ventas y compras, incluidos los campos `alvina_request_line_id`
de sus líneas. `fulfillment.py` conserva relaciones y dependencias que requieren
esos campos. Odoo puede fallar al reconstruir su registro después del reinicio
por esa inconsistencia, antes de atender la interfaz web.

La sintaxis Python y XML de los archivos recibidos es válida. Esa comprobación
no detecta relaciones con campos ausentes. Sin el error del servidor no se
afirma cuál fue la primera excepción ni que este sea el único problema presente.
El ZIP permite comprobar el defecto del paquete; no demuestra por sí solo qué
copia terminó cargando el proceso del servidor.

## Reproducción real del arranque y recuperación

Se preparó Odoo Community 19 oficial, revisión
`e1ed4fe077ba98ce7ac6802a43bb68242081dee9`, con PostgreSQL local aislado y una
base nueva desechable `alvina_incident_registry_test`. Se probó el addon del ZIP
recibido, sin instalar los demás módulos privados del ZIP.

Con el archivo incorrecto, el proceso terminó con código **255** al construir el
registro de modelos. La excepción reproducida fue:

```text
ValueError: 'alvina_request_line_id' declared in 'alvina.branch.request.line.sale_line_ids' does not exist on 'sale.order.line'.
```

Después se restauró **únicamente `models/commercial.py`** en aquella copia
temporal. Se repitió la instalación sobre **la misma base, sin borrarla ni
recrearla**: el proceso terminó con código **0**, cargó el registro y procesó
las vistas, seguridad y reportes del addon. Los nombres `test/` y `pre-migrate.py`
se dejaron como estaban durante esta prueba para aislar el efecto de cambiar
un solo archivo.

Después se arrancó un servidor HTTP accesible únicamente desde la propia
máquina de pruebas. La página de acceso devolvió **HTTP 200**; la autenticación
local fue correcta y `/odoo` devolvió **HTTP 200 con el backend autenticado**.
El servidor temporal se detuvo al terminar. La base conservó cero compras,
ventas, requerimientos y asientos, y el flujo central permaneció desactivado.

Esto confirma que el archivo defectuoso provoca un fallo de arranque y que
restaurarlo resuelve ese fallo en el entorno reproducido. No confirma todavía
el estado del servidor real, sus módulos Enterprise ni si su base terminó de
actualizarse. No se hicieron cambios en producción.

Registros locales de esta sesión: `/tmp/alvina-incident-bad.log` y
`/tmp/alvina-incident-restored.log`, con resumen en
`/tmp/alvina-incident-result.json`. Son evidencia temporal, no se incluyen
credenciales ni logs del servidor operativo en el repositorio.

Se encontraron además dos cambios de nombres respecto de `779f46d`:

- `tests/` pasó a `test/`, conservando el contenido. Esto puede omitir las pruebas
  en el descubrimiento habitual de Odoo; no explica la caída durante el arranque.
  El paquete de recuperación conserva el nombre canónico `tests/`.
- `migrations/19.0.1.1.0/pre-migration.py` pasó a `pre-migrate.py`, conservando el
  contenido. Ambos nombres cumplen el patrón `pre-*.py` del ejecutor de
  migraciones de Odoo 19. Este cambio no es la causa identificada del incidente.

## Alcance de la rama de recuperación

La rama `fix/requisition-startup-recovery` parte de `779f46d` y conserva el addon
`19.0.2.0.0`. Su archivo comercial ya era correcto: la copia defectuosa apareció
en el paquete operativo recibido, no en ese commit del repositorio de desarrollo.
Esta recuperación entrega la fuente correcta y comprobaciones del paquete;
no incorpora nuevas funciones comerciales ni revierte el esquema de la base.

La prueba estática de empaquetado comprueba archivos, importaciones, declaraciones
de campos y relaciones esperadas. No sustituye una instalación o actualización
de Odoo contra una base representativa. Los resultados históricos de la suite
Odoo están documentados en `TESTING.md`; no se presentan como una nueva ejecución
de esa suite completa durante este incidente. La reproducción de arranque
anterior sí se ejecutó durante esta recuperación.

Comprobaciones ejecutadas durante esta recuperación:

- `python tools/check_addon_package.py`: aprobado sobre la fuente correcta.
- El mismo comando sobre el addon del ZIP recibido: rechazado por los campos
  ausentes, la copia errónea y el nombre de la carpeta de pruebas.
- Paquete restaurado desde ese ZIP: 41 archivos idénticos, byte por byte, al
  addon revisado de `779f46d`; comprobación de enlaces aprobada.
- `python -m unittest discover -s tools -v`: 9 casos aprobados, incluidos tres
  que verifican el paquete correcto, la sustitución errónea y un archivo presente
  pero no importado. Compilación Python y `git diff --check` aprobados.

El chequeo se puede ejecutar sobre una carpeta externa sin modificarla:

```bash
python tools/check_addon_package.py /ruta/real/alvina_branch_requisition
```

## Procedimiento manual para el administrador del servidor

1. Conservar un respaldo recuperable de la base de datos, su filestore y la
   carpeta de código que está fallando. Identificar el servicio, configuración,
   ruta efectiva del addon y revisión desplegada. Trabajar primero sobre una
   copia de pruebas cuando esté disponible.
2. Comparar la carpeta operativa con el addon completo de esta rama. Si se
   confirma el mismo defecto y el resto del código coincide, restaurar
   **únicamente** `alvina_branch_requisition/models/commercial.py` desde esta
   rama. Comprobar su SHA-256 con la tabla anterior. No copiar el contenido de
   `branch.py` dentro de ese archivo. Conservar las personalizaciones ajenas al
   cambio y no sustituir otros addons.
   Para recuperar también el descubrimiento de pruebas, devolver `test/` a
   `tests/` si se confirma el cambio descrito arriba. El preflight seguirá
   señalando esa diferencia hasta corregirla, aunque ya estén restaurados los
   campos comerciales. El paquete completo de recuperación tiene los nombres
   canónicos.
3. Si hay otras diferencias desconocidas, detener la sustitución y revisar el
   paquete completo antes de mezclar versiones. El addon completo de esta rama
   sirve como referencia; no debe envolverse en otra carpeta intermedia ni
   instalarse como un addon con nombre diferente.
4. Evaluar el estado real de la base antes de elegir la siguiente acción. Si
   `19.0.2.0.0` ya terminó de actualizarse correctamente y solo se dañó este
   archivo después, restaurarlo no requiere una reversión de datos. El
   administrador puede realizar un arranque controlado y comprobar la interfaz.
   Si solo se copiaron archivos o la actualización quedó incompleta, puede haber
   campos, tablas, vistas o dependencias pendientes: un reinicio no los crea.
   Reproducir ese estado en pruebas y resolver la actualización específica del
   addon con la configuración real antes de aplicarla al servidor operativo.
5. Verificar acceso al backend, Compras y Ventas con sus usuarios habituales.
   No enviar requerimientos reales, confirmar órdenes ni validar movimientos
   para comprobar únicamente que se recuperó el acceso.

No ejecutar `-u all`, desinstalar el addon, borrar tablas/historial ni modificar
manualmente el estado de módulos para intentar saltar el fallo. Tampoco hacer
un `git reset` general del repositorio compartido. Restaurar código antiguo sin
conocer el estado de la base puede dejar vistas y reglas apuntando a campos que
ese código ya no declara.

## Segundo error: columna pendiente en la base

Después de restaurar el código, el usuario proporcionó este error del servidor:

```text
psycopg2.errors.UndefinedColumn: column sale_order.alvina_branch_request_id does not exist
```

El campo ya está declarado en Python, pero falta su columna en PostgreSQL. Esto
indica un esquema pendiente o una actualización incompleta. La traza pasa por
las notificaciones al consultar el nombre de una venta: Odoo precarga los campos
de `sale.order` y la consulta encuentra la columna ausente. Que aparezcan módulos
de chat en esa traza no cambia la columna que está fallando.

Restaurar el archivo permite construir el registro de modelos; **actualizar el
addon instalado** es lo que aplica sus campos y vistas a la base. Son pasos
distintos. Un reinicio no ejecuta esa actualización.

Con respaldo recuperable y el código completo correcto, el administrador que
pueda abrir Aplicaciones debe buscar `alvina_branch_requisition`, abrir el menú
del módulo instalado y pulsar **Actualizar**. Esperar a que termine y recargar
Odoo. **No desinstalar**: desinstalar puede eliminar los requerimientos y la
configuración propios del addon. Tampoco crear la columna manualmente con SQL:
esa sola columna no reemplaza la actualización de todos los campos, vistas,
reglas y dependencias de esta versión.

Si la interfaz no permite actualizar, el administrador del servidor debe usar
el ejecutable, usuario de servicio, configuración y base realmente desplegados,
en una ventana controlada sin procesos concurrentes sobre esa base. Ejemplo de
la actualización específica, sustituyendo las rutas y el nombre de base:

```bash
odoo -c /ruta/configuracion.conf -d BASE_CORRECTA \
  -u alvina_branch_requisition --stop-after-init --no-http
```

Verificar la finalización correcta antes de volver a arrancar el servicio.
La operación debe actualizar únicamente este addon y sus dependencias necesarias,
sin activar el nuevo flujo ni generar documentos para comprobar el acceso.
Si la actualización falla, conservar el error concreto; no saltar los bloqueos
de migración ni modificar el estado de módulos para forzarla.

`d59eea3` en Community; no acredita una actualización de producción ni una

## Límites que se mantienen

Desde este entorno no se accedió a la base ni al proceso del servidor operativo,
no se sustituyeron sus archivos y no se reinició ni actualizó producción. La
corrección del paquete no garantiza que desaparezca todo error HTTP 500: faltan
contrastar el código realmente cargado, el esquema instalado y las dependencias
del servidor.

Recuperar el arranque tampoco completa la integración Enterprise. Se mantienen
los límites descritos en `NATIVE_INTERCOMPANY.md` e `INTERCOMPANY_FLOW.md`,
incluido el adaptador interempresa pendiente y el caso de sucursales que comparten
compañía con Industria. No activar el nuevo flujo como parte de esta recuperación.
