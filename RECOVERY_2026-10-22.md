# Recuperación de Ventas — 22/10/2026

Al abrir una venta desde «Ventas por día», Odoo falla al consultar sus entregas.
El traceback facilitado termina en:

```text
psycopg2.errors.UndefinedColumn:
column stock_picking.alvina_dispatch_id does not exist
```

El código Python cargado declara el campo, pero la base todavía no tiene su
columna. La lectura estándar de `sale_stock` encuentra esa diferencia al calcular
las alertas de las entregas. No es un problema del filtro de fechas.

## Paquete comprobado

Se revisó el ZIP `alvinha-cybe (1).zip` indicado como desplegado, SHA256
`cfb67a0fbba5f8905d5623fe57b27ff6761789d990a9073a05716bc15518f3f1`.
Todos los archivos fuente del addon coinciden con el commit publicado `742bfde`,
salvo `alvina_branch_requisition/__manifest__.py`:

| Elemento | ZIP desplegado | Versión coherente |
| --- | --- | --- |
| Versión declarada | 19.0.1.0.1 | 19.0.3.0.0 |
| Dependencias de Ventas | Faltan `sale_management` y `sale_stock` | Ambas declaradas |
| Datos del flujo | Omite nueve XML de configuración, seguridad, vistas y reportes | Todos declarados |

El manifiesto antiguo impide cargar todos los componentes del flujo, aunque sus
archivos estén físicamente en la carpeta. El traceback confirma el esquema
pendiente; no permite determinar si se omitió la actualización o si una
actualización anterior falló. Son dos comprobaciones distintas.

Se preparó un ZIP completo corregido conservando las 313 entradas originales.
El único archivo cuyo contenido cambia es el manifiesto del addon. El resto de
los módulos privados queda idéntico al ZIP recibido. SHA256 del paquete corregido:
`397293c7d8a9048815e66d45cb69be19ec895f881d1d367ea368ebe6c0dacca3`.
El paquete y los módulos privados no se incorporan a este repositorio.

## Aplicación por el administrador de Odoo

1. Respaldar base y filestore mediante el procedimiento de la instalación.
2. Aplicar la carpeta completa `alvina_branch_requisition` de la versión
   19.0.3.0.0 en su ruta real de addons, incluido `__manifest__.py`. Conservar las
   demás rutas y módulos privados de la instalación.
3. Actualizar el módulo instalado **Alviña - Requerimientos de sucursales**
   desde Aplicaciones. No desinstalarlo. Si se usa consola, detener el servicio
   correspondiente y emplear su entorno/configuración/base reales:

```bash
/ruta/real/odoo-bin -c /ruta/real/odoo.conf -d BASE_REAL \
  -u alvina_branch_requisition --stop-after-init
```

4. Arrancar el servicio una vez terminada correctamente la actualización y
   comprobar la apertura de una venta y sus entregas. Revisar el resultado de la
   actualización si devuelve otro error; no omitir sus validaciones.

No crear solo la columna mediante SQL: también se necesitan las tablas,
relaciones, permisos, secuencias, vistas y reportes del módulo. Un reinicio o
«Actualizar lista de aplicaciones» no sustituye la actualización del módulo.

## Validación y alcance

El preflight comprueba ahora la coherencia del manifiesto también a partir de
los modelos/imports realmente cargados, en lugar de confiar solo en la versión
declarada. Sus regresiones detectan código v3 con manifiesto antiguo, dependencias
ausentes y XML omitidos; conservan la compatibilidad con el addon v2 auténtico.
Las comprobaciones Python de paquete/validación suman **25 pruebas aprobadas**.

Se reprodujo la incidencia en una base Community desechable con el addon v2 y
una venta ordinaria confirmada con entrega. Cargar Python nuevo y reiniciar sin
actualizar produjo el mismo `UndefinedColumn` del usuario. Después de ejecutar
`-u alvina_branch_requisition` con el manifiesto correcto, funcionaron tanto
`stock.picking.read` como `sale.order.read` incluyendo `json_popover`, la ruta
del traceback original. Se conservaron la venta y entrega originales y no se
generaron guías retroactivas. Logs locales:

- `/tmp/alvina-manifest-recovery-no-upgrade.log` — reproducción del error.
- `/tmp/alvina-manifest-recovery-targeted-upgrade.log` — actualización correcta.
- `/tmp/alvina-manifest-recovery-after-upgrade.log` — lecturas recuperadas.

La validación funcional previa del mismo código del addon consta de 176 pruebas
Odoo aprobadas y está documentada en [TESTING.md](TESTING.md). No equivale a
certificar todos los módulos Enterprise/privados de producción. Se mantienen
los [bloqueos de integración](NATIVE_INTERCOMPANY.md).

La revisión del ZIP detectó además una colisión de nombre de campo con el módulo
QR `alvina_stock_request`, si está instalado junto a este addon. Es una incidencia
de integración separada del error SQL confirmado. Corregir el manifiesto y
actualizar el esquema no resuelve por sí solo esa colisión; revisar el apartado
correspondiente de compatibilidad antes de habilitar el flujo completo.

Esta revisión no ejecuta comandos ni modifica base, archivos o servicio de
producción. Aplicar el paquete y actualizar la base son pasos operativos que
debe completar el administrador autorizado.
